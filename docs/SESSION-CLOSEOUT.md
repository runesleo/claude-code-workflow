# 会话收尾：把一次长对话变成下次能用的东西

[English](SESSION-CLOSEOUT.en.md) · **中文**

一次长对话结束时，里面 95% 的内容对下一次没有价值：失效的上下文、中途放弃的方案、报错和重试、已经被推翻的判断。剩下 5% 是真正该留下的——改了什么、还差什么、谁批准了什么。

收尾就是把这 5% 抽出来写进文件，其余全部丢掉。

我用这套六步用了半年多。它不是"写一份 PROJECT_STATUS.md"——那份文档解决不了本文要解决的问题，原因写在最后一节。

## 为什么不能只在对话里说

**说过不等于写下。** 下一次会话是一个全新的上下文，它读不到这次的聊天记录。所以"我们决定用方案 B"如果只存在于对话里，下次就等于没发生过。

**更麻烦的是它不会报错。** 少做一步收尾从来不抛异常，你不会在当场发现。等到两周后接手时，才发现某个决定没人记得、某个改动没人知道为什么。

所以下面每一步的判据都是同一个：**这一步产生了文件吗？** 没有产物的步骤等于没做，不管对话里说得多完整。

## 六步

三个 app（Claude Code / Codex / Cursor）跑的是同一套，因为它们共享同一批文件。

### 1. 有代码或配置改动 → 提交，并写清为什么

```bash
scripts/session-manifest-commit.sh --repo <repo> --files "<逗号分隔>" --message "<why>"
```

**解决的问题**：改动散落在工作区里，下次打开不知道哪些是这次改的、为什么改。

message 写"为什么"不写"改了什么"——改了什么 diff 里有，为什么只在你脑子里。

本次零改动就跳过，不要为了凑步骤造一个空提交。

### 2. 未完成项必须落到某张任务卡

未完成的事只有两个去处：某张卡的 `next_action`，或者跨线的 `inbox`。

**给不出落点，就不许说"剩余/待确认/回头再说"**——要么当场做完，要么明说"这件事不做了"并给理由。悬着的事项是下次会话最大的成本来源。

⚠️ **写任务卡必须用带锁的写入器，不能直接 `json.dump` 覆盖。**

```bash
scripts/task-write.py append-inbox <TASK_ID> \
  --field <line>_inbox --entry-json <file> \
  --receipt-id <id> --input-id <id>
```

这里的锁不是保险起见。任务卡天然是多 writer——三个 app 都会写同一批文件，靠"约定单 writer"防不住。2026-08-02 的实测：20 并发下朴素的 read-modify-write 只活下 1 条，**丢了 95%**。

同一天还遇到一个更隐蔽的形态：正文被并发吞掉了，但回执留在了 `external_input_receipts` 里。于是任何按回执校验的流程都判"已投递"，而卡的 owner 打开一看什么也没有，**全程没有任何报错**。

所以写完必须双向校验：

```bash
scripts/task-write.py verify <TASK_ID> --receipt-id <id>
# 要求 body_present 与 receipt_present 同时为 true
```

只查回执会被半残状态骗过去。反过来只查正文也一样——回执没写的话，按回执校验的流程会判"没送到"，而正文其实躺在卡里。**两半都不抛异常，唯一能分辨的是 verify 的返回。**

### 3. 有 gate 决策 → 追加一行判例

本次会话如果对某个需要人工批准的动作（部署、动钱、公开发布、破坏性清理）做出了**明确的批准或驳回**，追加一行到判例日志：

```json
{"date":"...","gate":"...","subset":"...","decision":"approve|reject",
 "reason":"...","consistency_key":"<gate>.<子集短语>","task":"...","approved_by":"..."}
```

**解决的问题**：同一类请求反复问人。攒够同 key 且一致的判例之后，这类决策可以提案成规则，不用每次都打断。

没有 gate 决策就跳过，不要补造。

### 4. 产生了 durable artifact → 更新对应的 RECENT.md

**解决的问题**：下次会话启动时的"最近发生了什么"。这个文件是 rollover 的起点。

没有就明确写 `recent_update: none`——**明确的"无"和漏掉是两回事**，前者说明检查过了。

### 5. 写回当日记录，并挑出真信号

追加到 `daily/YYYY-MM-DD.md`：本次碰过的任务、提交、在途项。然后扫一遍本次会话的 delta，挑 **0-3 条**真信号写进"今日发现"。

上限是 3 是故意的。什么都往里记等于什么都没记，下次不会有人读。

⚠️ **写日期前先执行 `date`。** 会话开头拿到的日期只在开始那一刻正确，长会话跨天之后它就是错的，而且看起来完全正常。这个坑我踩过：一个跨了四天的会话，七处产物写了错的日期，包括 daily 文件名本身——当天的记录写进了三天前的文件。

### 6. 自检

```bash
scripts/session-leftover-guard.py --text "<你最后那段回复>"
```

扫最后的回复里有没有"待确认""回头再说""剩余"这类悬空表述。有告警就回到第 2 步补落点，然后再收。

## 收益

- **下次接手第一句话就能干活**，不用重读几万 token 的上下文——不管接手的是换了模型的你自己，还是别人。
- **token 消耗明显下降**，因为 AI 不再反复扫已经作废的旧坑。
- **跨模型接力几乎零摩擦**：Codex → Claude → Cursor 读的是同一批文件，不需要交接说明。

## 和"写一份 PROJECT_STATUS.md"的区别

一份状态文档能解决"现在做到哪了"，但解决不了这三件事：

| | 单份状态文档 | 这套协议 |
|---|---|---|
| 多 app 并发写 | 后写的覆盖先写的，静默丢数据 | flock 锁 + 锁内重读 + 原子替换 |
| 送达确认 | 写了就算送到 | receipt + 双向 verify，半残状态可检出 |
| 决策沉淀 | 混在正文里，无法聚合 | 独立 append-only 判例日志，可按 key 聚合成规则 |
| 少做一步 | 不会被发现 | 第 6 步自检 |

差别不在于文档的详细程度，在于**有没有执行者**。规则写得再清楚，如果没有任何一步强制它发生，它就只是一段好看的文字。

这也是这套协议为什么放在三个 app 共同加载的文件里，而不是某一个 app 的 workflow 目录下——我早期版本就犯过这个错：规则只有一个 app 读得到，于是长期只有一个 app 在做收尾，另外两个安静地漏，**而少做几步从来不抛异常**。

## 怎么抄

直接从这六步开始。抄完之后自己补两样东西：**锁**（第 2 步）和**跨 app 的一致性**（同一批文件三个 app 都要能读到）。没有这两样，剩下的四步在单人单 app 时能用，多开一个窗口就开始丢数据。
