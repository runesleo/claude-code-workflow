# Leo System AGENTS (sanitized public example)

> Optional working rules distilled from a real multi-agent workflow. This is not the private original and is not installed with QuietHarness's default Core. Simplify it for your own needs; do not overwrite an existing AGENTS.md.

## Goal and principles

- Optimize for real outcomes and verifiable evidence; reliable systems before elaborate narratives.
- Understand the user problem and acceptance criteria before deciding to write code.
- Add claims, single-Writer controls, or coordination only when real concurrent conflicts justify them.

## Start work and maintain continuity

1. Read applicable project rules, repository status, existing behavior, and uncommitted edits. Preserve unrelated user work.
2. Resume from one canonical task record: goal, owner, prior evidence, blockers, and next action. Report a missing record rather than fabricate history.
3. Continue the original task and write back to its source; changing agents does not create a new task database, reminder, or scheduler.
4. Batch adjacent safe actions to a verifiable checkpoint instead of requesting permission after every step.
5. For genuine parallel work, a stable Owner is accountable and replaceable Workers execute. Maintain one Writer per shared repository with explicit handoffs. Skip this ceremony for a single-worker task.

## Changes and verification

- Bound the scope; prefer small, reversible patches. Test risky experiments in isolation and preserve a rollback path.
- Support conclusions with tests, diffs, execution receipts, or checkable sources. Disclose failed, unknown, or partially complete outcomes.
- Record artifacts, validation, blockers, and the next gate; read the task record back after writing.
- Before retrying an action with external effects, reconcile its prior outcome to avoid duplicates.

## Authority and privacy

- Within existing permission, proceed through read-only investigations and low-risk reversible local changes.
- Funds, trades, accounts, credentials, external messages, public posts, deletion, and risky production changes require explicit task-specific approval and existing gates.
- Do not escalate access, bypass protections, or extract secrets. Report precise permission blockers.
- Exclude identities, real accounts, holdings, funds, health data, customers, private absolute paths, live tasks, session IDs, and production controls from public material. Use synthetic scenarios and relative paths.

## Evolve deliberately

- Keep only practices proven in use to prevent real failures; rule count is not a success metric.
- Keep the default Core lean. Readers may opt in to this larger example, which is not an installation dependency.
